# 0.2.0: the designed header and footer

`@getquick/content` 0.2.0 and `getquick/gq-content` 0.2.0, released together.
Builds on the 0.1.0 pair. A minor release: nothing existing changes, and a
Site without a designed header serves exactly what it served before.

## What's new

Editors design a Site's header and footer as block patterns per route in
GETQUICK → Design → Header & Footer (GQ Design 0.4.2+). The content runtime
now stores and serves them:

- **Route selection.** `designRouteKey(content)` returns the GQ Design route a
  page is served with: `front-page`, `home` (the posts page), `single-post`,
  `page`, `single` (another post type), `archive`, `search`, and `page` for a 404. Entries record theirs (`EntryContent.designRoute`).
- **Stored with the chrome.** The chrome read fetches every route's header and
  footer (`designPattern`) and stores them in the chrome row, in D1. Requests
  never read WordPress for them. There is no new migration.
- **Delivered per page.** `publishedHome`, `publishedEntry` and `pageChrome`
  return the chrome with that page's route `header` and `footer`
  (`SiteChrome.header`/`footer`, absent where the route has none).
  `pageChrome(siteOrigin, route)` takes a route for pages the Site adds itself
  (default `page`).
- **Rendering.** `renderSiteHeader(chrome, { renderers })` and
  `renderSiteFooter(chrome, { renderers })` return the pattern as HTML in
  `<header class="gq-site-header">` / `<footer class="gq-site-footer">`, or
  null when there is none. They use `renderWordPressBlocks`, which now takes
  the same `renderers` option: a Site's renderers by block name, applied
  wherever the block appears. `designMenuItems(menuItems)` turns a menu-backed
  block's items (such as `getquick/header-navigation`'s) into a menu tree.
- **Fallback.** A route without a pattern, or a CMS without GQ Design's
  `designPattern` field, keeps today's logo and primary-menu chrome: both
  renderers return null.
- **Freshness.** The CMS plugin sends a new shared `patterns` settings event
  when a synced pattern, template, template part or navigation menu is saved,
  trashed or deleted, when a classic menu a pattern shows is saved, and when
  the theme switches.
  The Frontend then refreshes every language's chrome row and nothing else, so
  every page gets the change at once. `wp gq-events settings status|retry`
  lists it. Reconciliation catches up on a missed event.

See [ADR 0003](../adr/0003-serve-each-routes-designed-header-and-footer-with-the-site-chrome.md)
for the decisions and their limits. Patterns aren't per language yet, and an
undeclared Site block arrives without its attributes.

## Adopting it in an existing Site

The Site's layout is site-owned and created once, so an existing Site copies
this change by hand. It assumes the Site already serves through
`@getquick/content` and passes the page's `chrome` to its layout, as the
skeleton does. Bump both pins to 0.2.0 (`@getquick/content` in
`apps/frontend/package.json`, `getquick/gq-content` in `apps/cms/composer.json`),
then edit `apps/frontend/src/layouts/Layout.astro`:

```diff
 ---
+import { renderSiteFooter, renderSiteHeader } from "@getquick/content";
 import { copyFor } from "../lib/copy";
 …
 const xDefault = hreflang.find((alternate) => alternate.language.isDefault);
+// The header and footer an editor designed for this page's route in
+// GETQUICK → Design → Header & Footer; null keeps the Site's own below.
+// `renderers` renders the Site's own blocks (e.g. getquick/header-navigation)
+// as its content does: { "getquick/header-navigation": (block) => "<nav>…</nav>" }.
+const renderers = {};
+const designedHeader = renderSiteHeader(chrome, { renderers });
+const designedFooter = renderSiteFooter(chrome, { renderers });
 ---
 …
   <body>
-    <header class="site-header">
+    {designedHeader ? (
+      <Fragment set:html={designedHeader} />
+    ) : (
+    <header class="site-header">
       … (the logo, the primary menu and the language switcher, unchanged) …
     </header>
+    )}
+    {designedHeader && alternates.length > 0 && (
+      <nav class="language-switcher" aria-label={copyFor(language).languages}>
+        <ul>
+          {alternates.map((alternate) => (
+            <li>
+              <a href={alternate.route} hreflang={alternate.language.lang} lang={alternate.language.lang}>
+                {alternate.language.slug.toUpperCase()}
+              </a>
+            </li>
+          ))}
+        </ul>
+      </nav>
+    )}
     <slot />
+    {designedFooter && <Fragment set:html={designedFooter} />}
   </body>
```

A page the Site adds itself (a listing or search page, say) asks for its
route's chrome: `content.pageChrome(Astro.site?.origin, "archive")`. Without a
route it gets `page`'s, as a layout that looks the chrome up itself does now.

Style `.gq-site-header` and `.gq-site-footer` with the Site's CSS. The
patterns carry WordPress's block classes, as content does.

## Upgrading the pair

- No migration. Chrome stored by 0.1.0 is served unchanged (no designed
  header or footer) until the next refresh, `patterns` event or
  reconciliation stores the patterns.
- Install both halves together. A 0.1.0 Frontend answers the new `patterns`
  event with 400 (an unknown setting), and the CMS records it as failed
  (`rejected`). A 0.2.0 Frontend with a 0.1.0 CMS works, but nothing triggers its
  patterns refresh except reconciliation.
- Entries stored by 0.1.0 have no `designRoute`. They are served with
  `single-post`'s chrome if they have a date (posts), else `page`'s, until
  they are refreshed.
