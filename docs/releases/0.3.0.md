# 0.3.0: the CMS-selected header and footer

`@getquick/content` 0.3.0 and `getquick/gq-content` 0.3.0, released together.
Builds on the 0.2.0 pair. A minor release with one breaking type change (below);
there is no new migration and the publication format stays 1.

## What's new

Editors select a Site's header and footer as published synced patterns in GQ
Design's Header & Footer. The content runtime now stores and serves them with
the Site chrome. See
[ADR 0006](../adr/0006-serve-cms-selected-header-and-footer-patterns-with-site-chrome.md).

- **Stored with the chrome.** The chrome read asks for `designPattern` for one
  design route, `ContentConfig.designTemplate` (default `page`), and stores
  the header and footer block trees in each language's chrome row. They are
  promoted, retained through outages and reconciled with it. A malformed or
  unresolvable tree fails the read and keeps what is stored.
- **Served on every page.** `SiteChrome.header` and `.footer` are
  `{ title, blocks }`, or null when the region uses a template part or nothing
  published is selected (keep the Site's own header or footer then). Rows
  stored by 0.2.0 serve both as null until the next refresh.
- **Rendering.** `content.renderDesignPattern(pattern, { siteOrigin, blocks })`
  (and the pure `renderDesignPattern` from the root entry) renders saved HTML,
  a built-in `core/site-logo`, and the Site's renderers by block name. GQ
  Design's `getquick-design/container` keeps its layout as in content.
  `designMenuItems` turns a menu-backed block's `menuItems` into a menu tree
  with safe, internal links.
- **Consent.** With `consent` configured, the saved HTML in served patterns has
  its embeds rewritten into placeholders at delivery, as page bodies do.
- **Freshness.** The CMS sends a shared `patterns` settings event when a synced
  pattern, template, template part or navigation menu is saved or deleted, a
  classic menu a pattern shows by `menuId` is saved, pattern sync eligibility
  changes, GQ Design invalidates its layouts, or the theme switches.
  `wp gq-events settings status|retry` lists it; reconciliation repairs a
  missed one.

## Also in this release

- **Collections and archive Pages.** `ContentConfig.collections` stores public
  custom post types' items as entries; `content.list`, `content.terms` and
  `content.archiveUri` list them from the publication store alone. GETQUICK →
  Archives assigns each type a Page that takes over its archive address. Deploy
  the Frontend before the CMS plugin. See
  [ADR 0005](../adr/0005-store-collections-and-give-their-archives-to-pages.md).
- **Document metadata.** `@getquick/content/metadata` (with `/metadata/content`
  and `/metadata/testing`) builds a page's document
  metadata (title, description, canonical, alternates, share images) from
  stored entries.
- **Reconciliation.** Listed routes stored missing no longer hold every run
  `behind`: they settle until WordPress modifies them, and a few are re-read
  each run in case their address was freed.

## Breaking change

`SiteChrome.header` and `SiteChrome.footer` are required. Code that builds a
`SiteChrome` (test fixtures, a Site's own fallback chrome) adds
`header: null, footer: null`. Code that only reads the runtime's chrome needs
no change.

## Requirements

- **GQ Design 0.4.1 or newer** for the default `page` route (`single` and
  `search` need 0.4.2). GQ Design 0.2.17 to 0.4.0 answer null for `page`, so
  the Site keeps its own regions. Without `designPattern` at all (before
  0.2.17) the chrome is still read and served, with both regions null, and a
  warning names GQ Design and the version needed.
- Patterns aren't per language yet: every language is served the default
  selection
  ([gq-design #53](https://github.com/Quick-Release/gq-design/issues/53)).

## Adopting it

Bump both pins to 0.3.0 (`@getquick/content` in the Frontend,
`getquick/gq-content` in the CMS). The first refresh, `patterns` event or
reconciliation stores the selection. Render `chrome.header` / `chrome.footer`
with `content.renderDesignPattern` where the layout renders its header and
footer, keeping the Site's own when it returns an empty string (see the
Frontend README's "Header and footer patterns").
