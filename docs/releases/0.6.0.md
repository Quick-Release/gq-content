# 0.6.0: file uploads in headless Gravity Forms

Release `@getquick/content` and `getquick/gq-content` together from one retained
`v0.6.0` candidate. The prior stable pair was 0.5.1. Design 0.10.2 and wire
contract 2.1.0 are unchanged; no publication-store or consent migration is
added. The form descriptor's schema stays 1.

Gravity Forms **File Upload** fields are supported
([ADR 0010](../adr/0010-accept-gravity-forms-file-uploads-through-the-site-worker.md),
[configuring them](../forms-file-uploads.md)). Before, they failed readiness
with `unsupported-file-upload`.

- **CMS:** a `fileupload` field's descriptor carries `upload`:
  `allowedExtensions`, `maxFileSize` (bytes, capped by PHP's
  `wp_max_upload_size()`), `multipleFiles` and `maxFiles`. Settings the
  Frontend can't honour stay `unsupported-file-upload` diagnostics: no or
  unverifiable extensions (only `jpg`, `jpeg`, `png`, `gif`, `webp`, `pdf`),
  several files without a maximum, and a form whose largest upload exceeds
  PHP's `post_max_size` or `max_file_uploads`. Post image and signature fields
  stay unsupported.
- **`@getquick/content/forms/astro`:** an accessible `<input type="file">`
  with `accept`, `multiple` and a hint naming the accepted types, size and
  number of files. A form with one posts `multipart/form-data`, and its action
  names the page (`?gq_source=`). It still works without JavaScript.
- **`@getquick/content/forms/server`:** accepts `multipart/form-data` up to
  `maxUploadBytes` (10 MiB by default, 32 MiB at most). It checks each file's
  count, size, extension and content signature, never the client's MIME type,
  and keeps only the descriptor's inputs. It forwards the post to Gravity Forms'
  submissions endpoint as multipart (`input_<id>` or `input_<id>[]`), without a
  credential. Forms without uploads are still sent as JSON. A post over the cap
  returns to its page with the new `too-large` outcome. Gravity Forms'
  per-file messages (a list for multi-file fields) become the field's error.
- **`@getquick/content/forms`:** `validateUploads`, `sniffFileType`,
  `uploadFilename`, `hasUploads`, `largestUpload`, `FILE_TYPES` and
  `VERIFIABLE_FILE_EXTENSIONS`; the `file-type`, `file-size` and `file-count`
  error codes. `formsReadiness(descriptors, { maxUploadBytes })` warns about a
  form whose largest upload exceeds the Site's cap.
- **`@getquick/content/forms/testing`:** `SUBMISSION_FORM`,
  `IMAGE_AND_PDF_UPLOAD`, `SAMPLE_FILES`, `sampleFile`, `multipartBody` and
  `submissionValues`. `gravityFormsStub` accepts multipart and records files,
  and `assertAccessibleForm` checks file inputs. `UNSUPPORTED_FORM`'s upload
  diagnostic is now an upload of unverifiable `docx` files.

## Release gates and rollout

The required PR checks and the retained paired validation workflow must pass.
Its `forms-astro` proof now also attaches files in Chromium without
JavaScript, and P2 checks the upload descriptor and its diagnostics in real
WordPress. Publish only from the successful CI record, as in
[releasing](../releasing.md).

A Site adopts it through the blueprint: bump the `@getquick/content` and
`getquick/gq-content` pins to 0.6.0, `gq sync`, rebuild and deploy the CMS and
the Frontend together. A Frontend older than 0.6.0 drops the upload field it
doesn't know, so don't deploy the CMS alone. Then size each form's uploads
under the Site's limits (see [configuring uploads](../forms-file-uploads.md)).
